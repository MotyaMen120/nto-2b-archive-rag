# NTO 2B — Калибровка решений (`skip`/`no_info`) и контроль сабмита

## 1. Математика оптимального `skip`
Для вопроса $q$ с вероятностью правильного ответа $p$:
- При наличии правильного доказательства в топ-5 ($a_q = +1.0$ vs $-0.5$):
  $$E[	ext{answer}] - E[	ext{skip}] = 0.7 \cdot (1.5 p - 0.5) - 0.7 \cdot (-0.25) > 0 \iff p > rac{1}{6} pprox 0.167$$
- Без правильного доказательства ($a_q = +0.5$ vs $-0.5$):
  $$E[	ext{answer}] > E[	ext{skip}] \iff p > 0.25$$

**Практические правила**:
1. Не ставь высокий порог `skip` (например, `0.5`) — это убивает матожидание!
2. Калибруй вероятность `p_correct` на OOF (`GroupKFold`) с помощью логистической регрессии / LightGBM по фичам:
   - `top1_rerank_score`, `top1_minus_top2_margin`, `max_dense_sim`, `n_posts_above_thresh`;
   - `llm_confidence` / `self_consistency_agreement` (согласие между прогонами);
   - `answer_format` и признаки «сложности» вопроса (наличие расчётов дат, исторической проверки);
   - длина и полнота найденного таймлайна.
3. Подбирай порог `tau_skip` (возможно, отдельный для `number/date` и для `yesno/choice`, где случайное угадывание уже даёт 25–50%!) строго по максимуму OOF `S`.
4. **Критично**: для `yesno` случайная точность ~50% ($> 16.7\%$), для `choice` — 25% ($> 16.7\%$). Поэтому на `yesno` и `choice` `skip` выгоден почти никогда, кроме случаев полного провала поиска с инвертированной уверенностью. Основная польза `skip` — на `number` и `date` с низкой уверенностью!
5. Когда предсказываешь `skip`, **обязательно оставляй топ-5 `evidence`** (не пустую строку!).

## 2. Калибровка `no_info`
- В `train` всего 14/800 (1.75%) `no_info` (13 из них — `number`, 1 — `yesno`).
- Ложный `no_info` штрафуется как неверный ответ (`a_q = -0.5`, `e_q = 0`, итого `s_q = -0.35`), а верный `no_info` даёт `s_q = +1.0`.
- Предсказывай `no_info` только если:
  1. Максимальный скор реранкера ниже OOF-порога, И
  2. LLM-верификатор подтверждает, что в найденных постах `<= D` искомый факт (например, цена льготного билета, срок приговора, стоимость контракта) отсутствует (не путать с `promised`, когда событие анонсировано!).
- При `answer == "no_info"` всегда очищай `evidence = ""`.

## 3. Проверка лимитов T4 16 GB / 12 GB RAM / 6 часов
Перед финальной сдачей кода прогони dry-run с замером:
- Пик RAM (`tracemalloc` / `psutil.Process().memory_info().rss`) должен быть **< 9.5 GB** (запас под ОС и PyTorch).
- Пик VRAM (`torch.cuda.max_memory_allocated()`) должен быть **< 14.5 GB**.
- Полное время (индексация 142k постов + 400 вопросов) экстраполировано **< 4.5 часов** (запас 1.5 ч на приватный перезапуск организаторов).
- Проверь работу с `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`.
